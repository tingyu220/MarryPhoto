## 1. 项目概述

### 1.1 一句话定义

> 用照片、时间和文字，把姐姐结婚这一天完整保存下来。

技术只是承载方式。最终真正留下来的应该是：**人、照片、故事和记忆**。

### 1.2 这是什么

一个**私人婚礼数字影集**网站：把婚礼当天的大量照片，按照时间、人物、场景、精选程度、情绪和故事重新组织，形成一个兼具**纪念、展示、浏览、收藏**功能的长期数字影集。

### 1.3 命名

内部代号固定为 `wedding-memory`。

对外展示名（首页大字）待定，候选：

- OUR DAY（默认，最中性、最有电影感）
- 姐姐的婚礼 / 那一天
- The Day She Got Married

> 代码里所有对外文案走 `src/data/site.json`，改名只改一个文件。

---

## 2. 项目背景

姐姐结婚期间拍摄了大量照片（预计 300～800 张）。传统保存方式的问题：

| 方式 | 问题 |
| --- | --- |
| 微信发送 | 几天后被聊天记录淹没，画质被压缩 |
| 手机相册 | 没有故事线，只是一个按时间排的文件堆 |
| 网盘 | 只是文件存储，没有人愿意打开第二次 |
| 普通电子相册 | 浏览方式单一，几分钟就看完 |

结果就是：**很多年以后，很难重新感受到婚礼当天完整的时间、人物和情绪。**

---

## 3. 核心目标

项目**不是**建设复杂的照片管理系统，而是：

> 用尽可能简单的技术，做出一个具有高级感、情绪感和长期纪念价值的婚礼影集。

### 3.1 好看

第一眼不能像：后台管理系统 / QQ 空间 / 图床 / 网盘 / 婚庆公司模板网站。

而应该接近：**摄影作品集 + 电影影集 + 私人纪念册**。

### 3.2 好看照片（照片是绝对主角）

设计原则：

~~~text
照片 > 留白 > 文字 > UI
~~~

界面必须主动退让。禁止大量：卡片、边框、彩色按钮、装饰组件、图标、信息标签。

### 3.3 好浏览

同一批照片必须支持多种浏览方式，承担不同功能：

| 模式 | 解决的问题 | 使用场景 |
| --- | --- | --- |
| 精选 | 第一次来，不想翻 500 张 | 新访客、微信打开 |
| 故事 | 这一天发生了什么 | 完整看一遍 |
| 瀑布流 | 好看地看完所有照片 | 闲逛 |
| 联系表 | 快速找某一张 | 目标明确 |
| 胶片 | 慢慢看、沉浸 | 一个人安静的时候 |
| 时间线 | 完整时间记录 | 复盘那天几点在干什么 |
| 人物 | 只想看某个人 | 父母想看自己 |
| 随机 | 制造偶遇和回忆 | 反复访问的理由 |
| 全屏 | 所有模式的共同出口 | 看大图 |

## 4. 用户与隐私定位

### 4.1 用户优先级

1. **姐姐、姐夫**（第一优先级）
2. 父母、兄弟姐妹、家庭成员
3. 婚礼朋友、少量亲戚

### 4.2 因此不做

不注册、不登录、不做用户账户、不做社交系统、不做点赞排名、不做评论社区、不做后台 CMS。

### 4.3 核心场景假设

**姐姐在微信里点开链接。** 这一条决定了后面所有的技术与设计取舍：

- 必须移动端优先，2 列瀑布流，手指能顺畅滑动；
- 首屏下载量必须小（微信内置浏览器往往在移动网络下打开）；
- 不能依赖任何需要登录或额外授权的能力。

## 5. 设计原则（工程侧）

| 原则 | 落地方式 |
| --- | --- |
| 高内聚 | 照片数据、浏览、模式组件职责单一，一个组件只做一件事 |
| 低耦合 | 所有浏览模式共享同一个 `usePhotos()` 数据源，**绝不各自维护一套照片数组** |
| 最小复杂度 | V1 无后端、无数据库；静态站点 + JSON + 静态图片 |
| 可扩展 | 数据结构预留 video / voice / story 字段，但 V1 不实现 |

数据流是单向的：

~~~text
photos.json (生成)  +  photos.overrides.json (手写)
                │
                ▼
        usePhotos() / PhotoStore   ← 唯一的照片数据源
                │
   ┌────────────┼────────────┬──────────────┬─────────────┐
   ▼            ▼            ▼              ▼             ▼
Masonry    ContactSheet    Film        Timeline      Lightbox
~~~

### 6.1 顶层导航（页面级）

| 中文 | 英文 | 路由 | 版本 |
| --- | --- | --- | --- |
| 首页 | Home | `/` | P0 |
| 精选 | Featured | `/featured` | P0 |
| 这一天 | Story | `/story` | P0 |
| 全部照片 | Gallery | `/gallery` | P0 |
| 人物 | People | `/people` | V1.1 |

| 写给姐姐 | Letter | `/letter` | P0 |
| 随机 | Random | `/random` | V1.1 |

### 6.2 浏览模式（Gallery 内的视图，不是独立导航）

模式切换通过查询参数实现，可分享、可后退：

~~~text
/gallery?view=masonry      瀑布流（默认）
/gallery?view=contact      联系表
/gallery?view=film         胶片
/gallery?view=timeline     时间线
~~~

> 模式是"看同一批照片的四种方式"，所以必须是**同一个路由下的视图切换**，
> 而不是四个各自抓一遍数据的页面。筛选条件（scene/people/tag）同样进 URL：
> `/gallery?view=contact&scene=ceremony`。

### 6.3 导航行为

- 导航栏在所有页面顶部，滚动时隐藏、向上滚动时出现；
- 首页第一屏**不显示导航栏**（保持全屏照片的纯净），滚动后淡入；
- Letter 页面不出现在导航栏高亮里，它只在首页底部与页脚出现——
  它应该是"走完整条路以后的终点"，而不是一个可以顺手点开的标签。

## 7. 页面规格

### 7.1 首页 Home `/`

**职责：建立情绪，而不是展示全部内容。**

**第一屏（100vh）**：一张全屏婚礼照片 + 极简文字。

~~~text
（整屏照片，缓慢的呼吸感缩放 20s，随滚动淡出）

        OUR DAY

      姐姐 & 姐夫

      2026 · 09 · 16

        Explore ↓
~~~

- **只放一张，禁止轮播图。** 轮播会立刻带来"模板网站"的廉价感。
- 照片加一层极轻的暗角/渐变遮罩，保证文字可读。
- 首选竖构图或人物特写，避免远景（远景里人物太小，没有情绪）。
- 第一次进入用 600ms 淡入，文字延迟 200ms 依次出现。

**第二屏（承诺）**：

~~~text
这一天，我拍下了很多照片。

有些很漂亮，有些甚至没有对焦。

但我还是想把它们全部留下来。

View Memories →
~~~

**第三屏（精选横滑）**：12 张精选照片，横向滚动，点击进全屏。
**第四屏（入口）**：Story / Gallery / People 三个入口，用文字 + 一个小缩略图，**不要用三列卡片**。
**第五屏**：Letter 入口，只有一句话：`最后，有一封信想给你 →`

**验收**：不滚动就能感受到"这是一本影集"；首屏下载量 < 1MB。

---

### 7.2 精选 Featured `/featured`

- 数量：**20～40 张**，人工在 overrides 里标 `"featured": true`。
- 目的：第一次打开网站的人不需要浏览几百张照片，直接看到最值得看的。
- **布局是编辑式画册，绝不能是统一网格**：全屏大图 / 双列 / 单张居中大图 / 横向图片 / 大片留白，交替出现。
- 每 3～5 张插入一小段单行文字（时间或一句话），作为呼吸与节奏。
- 滚动时照片轻微上移 + 淡入，错开 80ms。

**验收**：把这一页截图给别人看，对方不会认为这是模板网站。

---

### 7.3 这一天 Story `/story`（最重要的页面之一）

按婚礼当天时间顺序，把照片组织成章。

| 时间 | 章节 |
| --- | --- |
| 07:30 | 清晨 |
| 08:20 | 化妆 |
| 09:40 | 准备出门 |
| 10:20 | 接亲 |
| 11:30 | 到达酒店 |
| 12:08 | 婚礼仪式 |
| 13:20 | 合照 |
| 18:00 | 晚宴 |

每章结构：

~~~text
时间（大号衬线数字）
标题
一句简单文字（一到两句，不要煽情）
3～10 张照片（先一张大图，其余小图错落）
~~~

- 章节数据写在 `src/data/story.json`，由人工撰写。
- 章节与照片的关联方式：**按时间自动归属 + 人工覆盖**。默认取该时间段内的照片，
  可用 `photoIds` 显式指定。
- 左侧的时间轴细线随滚动生长（用 CSS `transform: scaleY`，不用动画库）。

**验收**：第一次访问的人看完这一页，能说清楚"那天发生了什么"。

### 7.4 全部照片 Gallery `/gallery`

默认 **Masonry 瀑布流**。横图、竖图、方图、手机照片、相机照片可以自然组合。

顶部筛选（文字按钮，选中加下划线，**不要胶囊标签**）：

~~~text
全部 · 婚礼 · 家人 · 朋友 · 抓拍 · 现场 · 细节
~~~

- 移动端 **2 列**，桌面端根据宽度 3～4 列。
- 只加载缩略图（480px），进入视口前 400px 才开始加载。
- 使用 `aspect-ratio` + 主色背景占位，**杜绝布局抖动（CLS）**。
- 筛选变化时不做整页重排动画，只做一次 200ms 淡入。

---

### 7.5 联系表 Contact Sheet `/gallery?view=contact`

摄影师的看片方式，用于**快速找图**。

~~~text
001  002  003  004  005
006  007  008  009  010
011  012  013  014  015
~~~

- 等宽正方形裁切网格，桌面 5～6 列，移动 3 列。
- 每张左上角标序号（等宽字体，10px，低对比度）。
- 悬停：缩略图轻微放大 1.03，其余不变；**不加边框、不加阴影**。
- 点击：进入全屏浏览，序号在 viewer 顶部持续显示，方便"记住第几张"。

---

### 7.6 胶片 Film `/gallery?view=film`

承担"**慢慢看照片**"的职责。

- 一屏一张大图，居中；下方极简信息：编号 / 时间 / 简短描述。
- 滚动时一张一张出现，**禁止快速瀑布流**。
- 视觉参考：35mm 胶片、摄影作品集、编辑式画廊。
- 键盘：空格 / ↓ 下一张，↑ 上一张。

---

### 7.7 时间线 Timeline `/gallery?view=timeline`

与 Story 的区别：

| | Story | Timeline |
| --- | --- | --- |
| 性质 | 内容叙事，人工撰写章节 | 完整时间记录，数据驱动 |
| 内容 | 8 个章节、每章 3～10 张 | 每一张有时间的照片 |
| 文字 | 有人写的段落 | 只有时间 + 自动描述 |

布局：

~~~text
─────────────
08:23
[照片]
化妆开始
─────────────
09:41
[照片]
准备出门
─────────────
~~~

同一小时内的照片折叠成一组，可展开。以后可以插入视频节点。

### 7.8 人物 People `/people`（V1.1）

人工打标签（**V1 不做 AI 人脸识别**）。

- 人物：姐姐 / 姐夫 / 爸爸 / 妈妈 / 家人 / 朋友 / 伴娘伴郎 / 小朋友。
- 支持单选与组合：`只看姐姐`、`姐姐 & 姐夫`、`爸爸或妈妈`。
- 每个人物一个头像：取该人物照片里 **order 最靠前的一张** 做圆形裁切（全站唯一允许的圆角）。
  为什么不是「出现最多的一张」：对某个人物来说，`byPerson()` 返回的每一张都包含他，
  「最多」没有区分度；真要挑「最好看的一张」只能人工指定，那是 overrides 的事，不是页面的职责。
- 结构：人物卡片墙（圆形裁切 + 姓名 + 张数）→ 点进去是该人物的瀑布流。

### 7.9 瞬间 Moments `/moments`（V1.1）

专门展示**不一定最好看，但很真实**的照片：

姐姐突然笑、父亲坐在旁边、母亲整理衣服、姐夫紧张、小孩偷吃东西、
婚礼结束后的现场、家人聊天、工作人员准备……

- 标记方式：overrides 里 `"moment": true`（或在 tags 里加 `moment`）。
- 呈现：比 Gallery 更慢、更大、更少；每张配一句时间与描述。
- 这一页的文案应当朴素：`没人在看镜头的时候。`

---

### 7.10 随机 Random `/random`（V1.1）

一个按钮，一句文案：

~~~text
随机看看这一天
~~~

- 点击 → 全屏随机一张照片；再点 → 下一张。
- 键盘：空格切换。
- 可以带筛选：`随机看看姐姐`、`随机看看抓拍`。
- 行为细节：**不重复上一张**；每张照片在本次会话内的随机顺序使用洗牌队列，
  保证"刷一圈"能看完全部，而不是反复撞见同一张。

### 7.11 全屏照片浏览器 PhotoViewer（所有模式共享）

**这是全站技术含量最高的一个组件，必须只有一个。**

技术选型：**PhotoSwipe v5**（原生 JS，轻量，手势完善），外面包一层 Vue 组件。

| 平台 | 交互 |
| --- | --- |
| PC | ← → 切换、ESC 关闭、滚轮缩放、双击放大、底部信息条 |
| 手机 | 左右滑动、双指缩放、下滑关闭、点击隐藏 UI |

UI 极简：

- 右上角：`23 / 386`
- 底部（可开关）：时间 · 描述（与 docs/02 §6.5 一致，全站只有这一种写法）
- **不显示分享、下载、点赞、收藏等多余按钮。**
- 大图使用 preview（2048px），先显示 blur 占位，加载完成后 300ms 淡入。
- 键盘焦点管理：打开时焦点进入 viewer，关闭时回到触发它的缩略图。

### 7.12 写给姐姐 Letter `/letter`

- 内容是手写信的网页版，写在 `src/data/letter.json`（greeting / paragraphs / signature）。
- **不要一进网站就看到它**，它在整个浏览体验的最后。
- 配一张姐弟（或姐妹）小时候的照片，做成一张"夹在信里的小照片"：略微旋转、有白边。
- 排版像信纸：窄栏（`max-width: 34ch`）、大行高（1.9）、缓慢淡入。
- 页面极简：没有导航高亮、没有页脚干扰、滚动到最后只有签名。

体验曲线：

~~~text
婚礼 → 照片 → 故事 → 回忆 → 信
~~~

## 8. 数据模型

### 8.1 目录约定

~~~text
photos/original/**          原始照片（.gitignore，不进仓库）
public/photos/thumb/        480px  WebP  ← 列表、网格、联系表、时间线
public/photos/medium/       1280px WebP  ← 桌面端中等尺寸（画册版面、错落图）
public/photos/preview/      2048px WebP  ← 全屏大图、首屏
public/photos/blur/         20px   WebP  ← 渐显占位
src/data/photos.json        由脚本生成（技术信息）
src/data/photos.overrides.json  人工维护（人话）
src/data/story.json         人工撰写（Story 章节）
src/data/people.json        人物词典
src/data/letter.json        那封信
src/data/site.json          站名、日期、文案
~~~

### 8.2 photos.json（生成，禁止手改）

~~~json
{
  "generatedAt": "2026-09-21T12:00:00Z",
  "photos": [
    {
      "id": "P0001",
      "src": "/photos/preview/P0001.webp",
      "thumb": "/photos/thumb/P0001.webp",
      "medium": "/photos/medium/P0001.webp",
      "blur": "/photos/blur/P0001.webp",
      "width": 2048,
      "height": 1365,
      "ratio": 0.6665,
      "time": "2026-10-18T08:23:00",
      "color": "#8a7a6d",
      "order": 12
    }
  ]
}
~~~

- `width/height` 是 **preview 的实际像素**，用于 `aspect-ratio` 占位。
- `color` 是主色，用于加载前的背景，避免白闪。
- `time` 来自 EXIF 拍摄时间，缺失则退回文件修改时间，再缺失则置 null 并排在最后。

### 8.3 photos.overrides.json（人工，脚本永不覆盖）

~~~json
{
  "P0001": {
    "featured": true,
    "moment": false,
    "scene": "getting-ready",
    "people": ["sister", "mother"],
    "tags": ["family", "preparation", "candid"],
    "description": "妈妈帮姐姐整理衣服"
  }
}
~~~

**为什么分成两份文件**：脚本重跑一百次也不会冲掉人工标注。
运行时用 `usePhotos()` 把两份数据 merge 成最终对象；缺失的 overrides 使用默认值。

### 8.4 合并后的对象（应用内使用的形状）

~~~ts
interface Photo {
  id: string
  src: string; thumb: string; medium: string; blur: string
  width: number; height: number; ratio: number; color: string
  time: string | null
  order: number
  featured: boolean
  moment: boolean
  scene: Scene | null
  people: PersonId[]
  tags: Tag[]
  description: string | null
}
~~~

### 8.5 受控词表（V1 固定，不要随意扩张）

**Scene**：`preparation` `pickup` `ceremony` `family` `banquet` `after`

**People**：`sister` `groom` `father` `mother` `family` `friends` `bridesmaid` `groomsman` `kid`

**Tag / Type**：`portrait` `candid` `detail` `scene` `group` `moment` `preparation` `emotion`

> 词表定义在 `src/data/taxonomy.ts`，是**唯一**的分类来源。
> 中文显示名在 `people.json` / `taxonomy` 的 label 字段里，代码里只出现英文 key。

## 9. 图片处理管线（本项目最重要的工程问题）

### 9.1 为什么

15MB JPG × 500 张 = **7.5GB**。直接部署原图，网页永远打不开。

### 9.2 四层图片

| 层级 | 位置 | 规格 | 用途 | 进 Git |
| --- | --- | --- | --- | --- |
| Original | `photos/original/` | 原始 | 唯一母版，本地保存 | ❌ 忽略 |
| Preview | `public/photos/preview/` | 长边 2048px WebP q82 | 全屏查看器、首屏大图 | ✅ |
| Medium | `public/photos/medium/` | 长边 1280px WebP q78 | 桌面端中等尺寸展示（画册版面、Story 错落图、瞬间页） | ✅ |
| Thumb | `public/photos/thumb/` | 长边 480px WebP q72 | 所有列表（网格、联系表、时间线缩略图） | ✅ |
| Blur | `public/photos/blur/` | 长边 20px WebP q40 | 渐显占位 | ✅ |

四层一律"不放大"：比长边更小的图保持原尺寸（`withoutEnlargement`）。

**为什么要多一层**：桌面端的画册版面（Featured 的 pair / wide / offset）实际宽度是 580～880px，
Story 的错落图是 540～800px，都超过了 thumb 的 480px 长边（竖构图的 thumb 只有 320px 宽）——
把缩略图拉到 880px 就是 1.8～2 倍的插值放大，照片会明显发虚；而直接上 2048px 的 preview，
又是为 600px 的槽位下载 3 倍过采样的大图。medium 的 1280px 正好覆盖 640px 槽位的 2 倍屏：
**既不放大，也不浪费**。

### 9.3 脚本流程 `scripts/process-images.mjs`

~~~text
扫描 photos/original/**
        ↓
读取 EXIF（DateTimeOriginal / Orientation）
        ↓
分配稳定 ID（photos/index.json 做 id ↔ 文件名映射，已分配的不再变）
        ↓
按拍摄时间排序，写 order
        ↓
sharp: 自动旋转 → thumb / medium / preview / blur + 主色
        ↓
写 src/data/photos.json
        ↓
校验 overrides（缺失项、孤立 ID、拼错的词表 key）
~~~

常用命令：

~~~bash
npm run photos          # 处理新增照片（增量：已存在的 ID 直接跳过）
npm run photos:force    # 全部重新生成
npm run photos:check    # 只校验，不生成
~~~

### 9.4 关键设计决策

1. **增量处理**：只处理 index 里没有的新文件，婚礼后加 300 张只需要几十秒。
2. **ID 稳定**：ID 一旦分配永不改变，overrides 永远有效。
3. **方向自动纠正**：读取 EXIF Orientation 并 `rotate()`，杜绝横竖颠倒。
4. **生成与标注分离**：见 8.3。
5. **可重入**：任何时候删掉 `public/photos/` 重跑，结果一致。
6. **占位期与真实期必须分清**：占位图在 `index.json` 里登记为 `placeholder/P####.svg` 伪路径。
   真实照片第一次导入时会清理这批伪记录，**ID 会重新分配**，因此占位期间写的
   `photos.overrides.json` 会指向别的照片 —— 导入前必须先清空 overrides（见 README）。
7. **没有原图时不覆盖生成物**：`photos/original/` 为空时脚本直接退出，
   绝不把已有的 photos.json 抹成空数组。

依赖：`sharp`（快、跨平台）、`exifr`（轻量 EXIF）。

## 16. 隐私与部署

### 16.1 事实

**GitHub Pages 本质是公开静态网站。** 前端做一个"输入密码"页面**不是安全措施**——
图片 URL 依然可以被任何人拿到。

### 16.2 两个方案

| 方案 | 说明 | 何时用 |
| --- | --- | --- |
| A：GitHub Pages | 免费、简单、快 | 照片可以接受半公开 |
| B：**Cloudflare Pages + Cloudflare Access**（推荐） | 真正需要邮箱验证才能访问 | 家庭照片需要真正限制访问 |

**决定（2026-09-21 确认）：正式版先走方案 A（GitHub Pages）。**

理由：免费、简单、方便；家庭内部传播足够。**但必须知情**：
仓库与图片资源对任何知道 URL 的人都是公开的，`noindex` 只挡住搜索引擎，挡不住人。

因此附加三条缓解措施（不做完不许公开部署）：

1. 仓库设为 **private**（GitHub Pages 在 private 仓库上需要 Pro；若用免费账号发布，
   则照片目录会被公开索引，必须重新评估）；
2. 站点不发布任何包含真实姓名、地址、单位、车牌的文字与照片；
3. 一旦照片涉及隐私顾虑，**立刻**切到方案 B（Cloudflare Pages + Access），
   切换成本很低：本项目是纯静态产物，换一个托管平台即可，代码不需要改动。

开发阶段本地预览即可，部署留到照片导入完成时执行。

### 16.3 SEO

- `index.html` 加 `<meta name="robots" content="noindex,nofollow">`
- `public/robots.txt`：`User-agent: *` / `Disallow: /`
- 不加 sitemap，不加任何站点统计脚本。

## 21. 最终定义

这个项目不是：

> 做一个放婚礼照片的网站。

而是：

> **用照片、时间和文字，把姐姐结婚这一天完整保存下来。**

技术只是承载方式。最终真正留下来的应该是：

**人、照片、故事和记忆。**
