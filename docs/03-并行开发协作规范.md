# 并行开发协作规范

> 本文档定义：**本会话作为总控，如何指挥多个独立上下文同时开发这个项目。**
> 配套：`docs/01-开发计划书.md`（做什么）、`docs/02-UI设计契约.md`（长什么样）。

---

## 1. 结论：可以，但要分清三种"多开"

| 方式 | 怎么做 | 独立性 | 结果回传 | 适用 |
| --- | --- | --- | --- | --- |
| **A. 子代理（推荐）** | 我在**当前会话**里派发 `subagent` / `subagent_fork` | 每个子代理有**独立的上下文窗口**，看不到本对话（除非用 fork），互不干扰 | 完成后**自动回传**结果与总结给我 | 全部开发任务 |
| **B. 手动多开对话** | 你自己在 GUI 里新开几个对话，把我给的任务卡粘进去 | 完全独立 | **不会自动回传**，需要你复制结果给我 | 你想亲自参与/旁观某个任务时 |
| **C. 大规模编排** | `workflow` 脚本一次性扇出几十个代理 | 独立 | 结构化汇总 | 全量照片标注、批量审查等 |

**答案：可以多开，而且推荐 A。** 但要注意三点现实约束：

1. **我无法替你打开新的 GUI 对话标签页**——我只能派子代理。
   子代理在系统里是真实存在的独立会话（有 id、可以被继续对话、可以被中断），
   效果等价于"另开一个对话在别处干活，干完把结果交回来"。
2. **并行不等于无脑并行。** 真正决定成败的不是"开几个对话"，
   而是**接口有没有先冻结、文件所有权有没有互斥**。没有这两条，开 8 个代理只会
   产生 8 份互相冲突的代码。
3. **验证权必须留在总控（本会话）。** 子代理会自信地报告"已完成"，
   所以每个任务的完成都由我实际跑一遍（`npm run build`、看页面、量体积）才算数。

### 因此本项目的分工是

~~~text
总控（本会话）
  ├── 维护 docs/01 作为唯一真相源，拆任务卡
  ├── Wave 0：亲自冻结接口（这一步绝不外包）
  ├── 派发并行子代理，每个代理只写白名单里的文件
  ├── 审核、验证、合并、更新文档
  └── 对最终视觉与体验负责（Home / Featured 亲自做）
~~~

## 2. 三条铁律

### 铁律一：接口先冻结，再并行

Wave 0 结束前不允许任何并行开发。冻结的东西：

| 冻结物 | 文件 | 为什么 |
| --- | --- | --- |
| 数据类型 | `src/types/photo.ts` | 四个浏览模式组件全靠它 |
| 分类词表 | `src/data/taxonomy.ts` | 筛选、人物、标签共用 |
| 设计 token | `src/styles/tokens.scss` | 所有组件引用，不各写各的颜色 |
| 数据访问契约 | `composables/usePhotos.ts` 的**签名** | 只冻结签名，实现可以在 Wave 1 里做 |
| 示例数据 | `src/data/photos.json`（20 条占位） | 让并行任务都有东西可跑 |

冻结之后，**任何一方要改接口，必须停下来先通知总控**，由总控改完再通知所有相关代理。

### 铁律二：文件所有权互斥

同一时间，一个文件只能有一个写入者。
共享文件（router、token、taxonomy、photos.json）**只有总控能改**。

### 铁律三：完成必须有证据

每个任务卡的"完成定义"里必须包含**可执行的验证命令**与**期望输出**。
"我写完了"不是完成。

## 5. 什么时候并行，什么时候必须串行

**适合并行**：互不 import 的组件、脚本工具、独立页面骨架、文档撰写、
批量数据标注、只读审查（视觉走查、性能审计）。

**必须串行**：脚手架初始化；接口/类型定义；设计 token；路由注册；
依赖升级（`package.json` 是全局共享文件）；构建配置；最终合并与验收。

**并行度的上限是 4**。超过 4 个并发，冲突排查与验证成本会超过收益；
验证类任务（只读）可以额外并行。

---

## 6. 汇报与验证的规矩

1. 子代理必须在汇报里贴**原始命令输出**，不是"我测试通过了"。
2. 总控收到汇报后，**独立复跑一次**关键验证命令。
3. 汇报与实际不符（例如声称 build 通过但实际报错）→ 该任务判为未完成，
   任务卡重发并附上真实错误。
4. 每个 Wave 结束后总控更新文档与本文件的状态表。
5. 只读审查任务（视觉/性能）**不允许修改任何文件**，只输出问题清单。

### 环境注意事项（每个代理都会碰到）

本项目所在环境有文件沙箱，实测结论如下：

| 命令 | 结果 | 规避方式 |
| --- | --- | --- |
| `npm install` | ❌ 写全局缓存被拒（EPERM） | 改用 `--cache .npm-cache`，并加 `--ignore-scripts`（生命周期脚本 spawn 会被拒） |
| `npm run build` | ❌ esbuild 启动子进程被拒（EPERM） | 由总控以提升权限执行；代理日常用 `npm run typecheck` 验证 |
| `npm run typecheck` | ✅ 正常 | 代理的标准验证手段 |
| `node scripts/*.mjs` | ✅ 正常 | 管线脚本可放心运行 |
| 编辑文件（edit/write） | ⚠️ dev server 运行时可能 `ReplaceFileW EIO` | 先停掉 dev server 再改文件；改完再启动 |

另外总控新增了一件公共验证工具（所有代理都应该用）：

| 命令 | 作用 |
| --- | --- |
| `npm run render-check` | 无浏览器渲染检查器：Node 里用 vue/compiler-sfc + sass + vue/server-renderer 真编译真渲染组件并跑断言（SSR 不执行 onMounted/手势，交互仍需真机走查） |
| `npm run render-check <关键字>` | 只跑文件名含关键字的检查 |

每个代理都必须提交自己的 `scripts/checks/*.mjs`，断言落在**渲染出的 DOM 与样式类**上。

**命名约定：`scripts/checks/NN-名字.mjs`（两位编号开头）**。不符合这个命名的 .mjs 会被跳过并提示 ——
检查目录里出现过代理留下的临时 dump 文件，它一旦 import 失败就会拖垮整轮检查。
运行器现在已做到"单个检查文件加载失败只影响自己"。

## 8. Wave 5 · 真实照片导入日清单（婚礼后执行）

按顺序做，任何一步没做完不要进下一步：

1. 备份原图（相机卡 / 手机相册 至少两处），原图放进 `photos/original/`；
2. `echo "{}" > src/data/photos.overrides.json` —— 清掉占位期的标注
   （占位 ID 会被重新分配，旧标注会指向错的人）；
3. `npm run photos` —— 生成四层图（thumb/medium/preview/blur）与新的 photos.json，检查脚本输出的体积统计；
4. `npm run photos:check` —— 看还有多少张没写描述；
5. 人工标注：精选（20~40 张）、人物、场景、瞬间、描述；
6. 写 `src/data/story.json` 的章节文案与 `src/data/letter.json` 的那封信；
7. `npm run typecheck && npm run render-check && npm run build` 三连；
8. 真机走查（微信内置浏览器 / iOS Safari / Android Chrome）；
9. 部署。
